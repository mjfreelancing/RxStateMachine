# 01 — Project Foundations

**Builds on:** nothing. **Prefix:** `FND`.

## Feature input (paste into `/speckit-specify`)

Establish the RxStateMachine project so every later feature is built and verified the same way: a
single multi-targeted NuGet package, an automated build-and-test pipeline on GitHub Actions with
plainly commented workflows, quality gates (formatting, analyzers, coverage, documentation
completeness, public-API tracking, vulnerability scanning), a benchmark harness, and a place for
runnable samples. No state machine behaviour is delivered here; the goal is a green,
empty-but-complete pipeline ("walking skeleton").

## Requirements

**Package and targets**
- FND-01 The repository MUST produce one NuGet package named `RxStateMachine`, MIT licensed, with
  README, license expression, repository URL, and icon in its metadata.
- FND-02 The package MUST target `netstandard2.0`, `net10.0`, and `net11.0`. Earlier `net*` targets
  are not carried: .NET 8 and .NET 9 both reach end of support in November 2026. Public behaviour
  MUST be identical on every target.
- FND-03 The only runtime dependency MUST be `System.Reactive` 6.x (plus the BCL and unavoidable
  compatibility backports).
- FND-04 Multi-targeting differences MUST be confined to the `IsExternalInit` and
  `RequiredMemberAttribute` shims and narrow, commented `#if` gates. Both shims MUST be declared
  `internal`, so they cannot collide with a consumer that defines its own.
- FND-05 Every timestamp the machine produces MUST come from the injected scheduler's clock, so
  timestamps are deterministic under virtual time (DD-22). `TimeProvider`, `DateTime.Now`, and
  `DateTimeOffset.UtcNow` MUST NOT be used to produce them, and `TimeProvider` MUST NOT appear in
  the public API.

**Build and quality gates**
- FND-06 Nullable reference types MUST be enabled and warnings treated as errors in all projects.
- FND-07 A committed `.editorconfig`, repository-wide build properties, and central package version
  management MUST define style, analyzer level, and versions once.
- FND-08 Formatting MUST be verified in CI; a violation fails the build.
- FND-09 The public/`internal` boundary MUST be explicit and the public API surface MUST be tracked in
  a committed baseline so any addition or removal is visible in review.
- FND-10 Every public member MUST have XML documentation; a missing comment is a build error.
- FND-11 The package version MUST come from a single source; builds MUST be deterministic and include
  source-link information and symbol packages.
- FND-12 Package validation MUST run on every pack: framework-compatibility validation, so the
  public surface of each target asset is checked against the others (FND-02); and baseline
  validation against the previous release for stable releases, skipped when no previous release
  exists (FND-E8).
- FND-13 Dependencies MUST be scanned for known vulnerabilities on every change and by a scheduled
  workflow (at least weekly). A failed scheduled run is the notification (GitHub emails the
  maintainer); no custom alerting is required.
- FND-14 A `SECURITY.md` MUST exist. Release notes are generated by the platform; no changelog file
  is maintained.

**Tests, benchmarks, samples**
- FND-15 A unit-test project MUST exist and MUST run the same suite on every target runtime.
  `netstandard2.0` is not a runtime: while it is a target, that same suite MUST also run on a
  runtime that resolves the `netstandard2.0` asset (for example `net48`), so its compatibility code
  path is executed rather than merely compiled. Property-based testing and virtual-time (Rx
  `TestScheduler`) support MUST be available to tests.
- FND-16 Line coverage of the core engine MUST be collected in CI, with an 80% floor that fails the
  build when not met. The floor is enforced only once the core assembly contains executable code
  (FND-E9).
- FND-17 A benchmark project MUST be runnable locally so a before/after comparison can be made on
  the same machine when a feature touches the hot path. There is no stored baseline and no CI
  latency threshold, because timings are not comparable across machines. The zero-allocation
  guarantee (DD-22: zero bytes per steady-state transition) MUST be enforced on every change by a
  deterministic test, on every target runtime whose BCL exposes a per-thread allocation measurement;
  where a runtime does not, the limitation MUST be stated rather than hidden.
- FND-18 A samples area MUST exist; every sample MUST be built and run in CI. An empty samples area,
  or a single placeholder sample, MUST pass (FND-E9).

**Continuous integration (GitHub Actions)**
- FND-19 On every push to `main` and every pull request, CI MUST restore, build every target with zero
  warnings, run all tests on every target, check formatting, run analyzers, build and run samples,
  pack, validate the package, and scan dependencies. A red build MUST block a release, and MUST block
  merging when a pull request is used.
- FND-20 Publishing MUST be a separate, explicit, CI-only step that is safe to re-run without
  creating a duplicate release, and MUST NOT be possible from a developer machine. It MUST be
  triggered only by a version tag and MUST run only if the build and test jobs pass. In this feature
  the publish job is built and exercised against a dry run or local feed only; registering on a
  public feed is out of scope.
- FND-21 Every workflow file MUST begin with a plain-language comment explaining what it does, when it
  runs, and what it needs; every step MUST have a readable name.
- FND-22 Secrets MUST live only in the platform secret store, never in files.
- FND-23 Third-party actions MUST be pinned to a full commit SHA or an exact version, and every
  workflow MUST declare least-privilege `permissions`.
- FND-24 Workflows MUST cancel superseded runs on the same pull request and MUST cache package
  restores, without the cache ever hiding a failure.
- FND-25 The repository MUST note, in a few lines, any setting that cannot live in files. A ruleset on
  `main` requiring the CI checks to pass is optional, since pull requests are optional.

**Branching**
- FND-26 The repository uses trunk-based development: short-lived branches merge to `main`, by pull
  request or directly. CI runs on pull requests and on pushes to `main`; publishing runs only on
  version tags.

## Edge cases and failure modes
- FND-E1 A first run on an empty library (no features yet) MUST be green.
- FND-E2 A pre-release version tag and a stable tag MUST both be handled; re-publishing the same
  version MUST not fail destructively or create duplicates.
- FND-E3 A change from a contributor's fork MUST not require secrets to build and test.
- FND-E4 A target framework that is unavailable on the CI machine MUST fail with a clear message.
- FND-E5 A dependency with a newly disclosed vulnerability fails the scheduled scan even when no code
  changed.
- FND-E6 A new public member without documentation, or with an unrecorded API change, fails the build.
- FND-E7 `net11.0` may be served by a preview SDK. This is accepted and gets no carve-out: every
  declared target builds and is tested like any other, and a failure on a preview SDK is an ordinary
  failure. CI MUST install the required SDKs explicitly; if a required SDK cannot be installed the
  build fails with a clear message (FND-E4).
- FND-E8 The first release has no previous version to validate against; package validation is skipped
  with a logged reason rather than failing.
- FND-E9 With no executable core code and no samples yet, the coverage gate (FND-16) and the sample
  run (FND-18) pass vacuously with a logged note, not a divide-by-zero or a failure.

## Design decisions relied on
DD-22 (how targets are measured).

## Success criteria
- SC-1 On a fresh clone, one documented command builds and tests every target locally.
- SC-2 The first CI run on the empty library is green on every target.
- SC-3 Introducing an undocumented public member, an unrecorded API change, a formatting violation, or
  a vulnerable dependency each independently turns CI red.

## Proposed defaults (tool choices to confirm in `/speckit-clarify` or `/speckit-plan`)
Tool names are kept out of the requirements above; these are the intended picks.
- **Versioning:** MinVer, deriving the version from git tags (alternative: Nerdbank.GitVersioning if
  a committed version file is wanted).
- **Coverage:** Coverlet (Cobertura output) with ReportGenerator for the summary, scoped to the core
  assembly, 80% line floor.
- **Benchmarks:** BenchmarkDotNet locally, used for before/after comparison on one machine.
  Allocation is enforced by a unit test (`GC.GetAllocatedBytesForCurrentThread`).
- **Property-based testing:** FsCheck.
- **Unit tests:** xUnit.v3 (the `xunit.v3` packages). If `netstandard2.0` is kept, confirm xUnit.v3
  supports the runtime chosen for its test leg (FND-15) before committing to it.
- **Branching:** trunk-based (FND-26). Revisit only if old major versions must be maintained.

## Open questions (for `/speckit-clarify`)
- Confirm the proposed defaults above.
- **Whether to keep `netstandard2.0` as a target.** It is the only thing that makes the package
  usable from .NET Framework 4.7.2+/4.8, and it is also the only source of the shims and `#if` gates
  (FND-04), an extra Windows CI leg for the `net48` test run (FND-15), and `System.Reactive`'s .NET
  Framework compatibility closure, which consumers on non-SDK projects resolve with binding
  redirects. Decide deliberately — keep it and plan for that cost, or target `net10.0`/`net11.0`
  only. Nothing outside this brief depends on the answer.
- Decided: the scheduled scan runs weekly and a failed run is the notification (FND-13); pre-release
  and stable packages both go to nuget.org, distinguished by the MinVer version suffix; a preview
  SDK serving a declared target is accepted and gets no separate gate (FND-E7).

## Out of scope
Any state machine behaviour; registering the package on a public feed before the final deliverable
(decided at release time); a generated documentation site or user guides (the XML documentation is
the API reference); mutation testing.
